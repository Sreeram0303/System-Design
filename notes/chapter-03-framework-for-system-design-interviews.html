Chapter 3 — A Framework for System Design Interviews

No one expects a production-grade system in 45 minutes. The interview simulates two engineers collaborating on an ambiguous problem — the process you demonstrate matters more than the design you land on.

01 What interviewers are actually evaluating

Not just technical design skill. A good session reads for the ability to collaborate, work under pressure, and resolve ambiguity constructively — and the ability to ask good questions, which many interviewers specifically look for.

Don't be like Jimmy — the student who always answers first, whether or not he actually knows the answer. Answering fast with no clarification isn't a bonus; this isn't a trivia contest, and there's no single right answer.
Red flags
  • Over-engineering — chasing design purity, ignoring tradeoffs and their compounding real-world cost.
  • Narrow-mindedness, stubbornness, resisting feedback.

02 Step 1 — Understand the problem, establish scope

Slow down. Ask before proposing. If the interviewer asks you to make an assumption instead of answering directly, write it down — you'll need it later.

Questions worth asking

  • What specific features are we building?
  • How many users does the product have?
  • How fast is the company expecting to scale — 3 / 6 / 12 months out?
  • What's the existing tech stack — what can we leverage instead of building from scratch?

Example — clarifying "design a news feed system"

CandidateIs this a mobile app, web app, or both?
InterviewerBoth.
CandidateWhat are the most important features?
InterviewerAbility to make a post and see friends' news feed.
CandidateReverse-chronological, or a weighted/ranked order?
InterviewerKeep it simple — reverse chronological.
CandidateHow many friends can a user have?
Interviewer5,000.
CandidateWhat's the traffic volume?
Interviewer10 million daily active users.
CandidateText only, or media too?
InterviewerImages and videos too.

Why these questions matter

Each one collapses a specific axis of the design space, before any box gets drawn:

QuestionDesign axisWhat changes with a different answer
Mobile, web, or both?Client surface"Both" forces a platform-agnostic API instead of server-rendered pages, plus push notifications and bandwidth-conscious media delivery for mobile.
Most important features?ScopeWithout this, "news feed system" is unbounded — comments, likes, notifications, search could all be in scope. This pins it to exactly two flows: publish + retrieve.
Chronological or ranked?Behavior / complexityRanked (EdgeRank-style) needs a whole scoring/ML subsystem — arguably a separate interview by itself. Chronological is just "sort by timestamp." Same feature, order-of-magnitude difference in what gets built.
How many friends can a user have?Fan-out shapeBounded (5,000) makes fan-out-on-write cheap and predictable — one post, ≤5,000 writes. Unbounded (Twitter-style followers) breaks that for celebrities, forcing a hybrid push/pull model. This decides the write-path architecture (Chapter 11).
Traffic volume?Scale inputsFeeds Chapter 2's back-of-envelope math directly → QPS/storage estimates → whether sharding, replication, or a cache tier (Chapter 1) are needed. At 10M DAU × up to 5,000 friends/post, synchronous fan-out would spike hard — why real designs push it through an async message queue.
Text only, or media too?Data shapeMedia needs object storage + a CDN (Chapter 1) and probably async transcoding/thumbnailing; text alone could live in a database. Storage math shifts by orders of magnitude — the same asymmetry as Chapter 2's Twitter example (140 B text vs. 1 MB media).

A sharper set of categories to ask through

  1. Scope — what does the system do, at minimum?
  2. Behavior / complexity — for a feature that exists, how sophisticated does it need to be?
  3. Fan-out / relationship shape — how many things does one action touch? Bounded vs. unbounded is what actually decides push vs. pull architecture — a different question from raw user count.
  4. Scale inputs — the raw numbers (DAU, actions/user/day, size/action) that feed the Chapter 2 math. The trigger for "this needs a big-scale design" isn't a headcount threshold to eyeball — it's what the QPS/storage numbers come out to once you run the math.

03 Step 2 — Propose high-level design, get buy-in

Reach agreement on a blueprint — treat the interviewer as a teammate, not an examiner.

  • Sketch box diagrams: clients, APIs, web servers, data stores, cache, CDN, message queue.
  • Run back-of-the-envelope math to sanity-check the blueprint against scale constraints (Chapter 2). Narrate it out loud.
  • Walk through concrete use cases — this surfaces edge cases you haven't considered.
How low-level should this get?

Depends on the problem. API endpoints and DB schema are too granular for "design Google Search" — but entirely fair game for "design the backend of a multiplayer poker game." Ask, or read the interviewer's cues.

Example — news feed, high level

Splits into two flows: feed publishing (a post is written to cache/DB, then fanned out into friends' news feeds) and news feed building (aggregate friends' posts in reverse-chronological order).

04 Step 3 — Design deep dive

By now: scope is agreed, the high-level blueprint is sketched and has feedback, and you have hints on where to go deeper. Work with the interviewer to identify and prioritize which components deserve it — it varies:

  • Senior-level interviews often push toward performance characteristics: bottlenecks, resource estimation.
  • URL shortener → the hash function design is the interesting part.
  • Chat system → latency reduction and online/offline status are the interesting parts.
Manage your time

It's easy to get pulled into details that don't demonstrate ability — going deep on Facebook's EdgeRank ranking algorithm burns precious time without proving you can design a scalable system.

05 Step 4 — Wrap up

  • Identify bottlenecks and discuss improvements. Never claim the design is perfect — there's always something to improve, and this is your chance to show critical thinking.
  • Recap the design — especially useful after a long session with multiple proposed approaches.
  • Talk through error cases: server failure, network loss, etc.
  • Mention operational concerns: metrics/error-log monitoring, rollout strategy.
  • Discuss the next scale curve — e.g. "this supports 1M users; what changes to reach 10M?"
  • Propose further refinements you'd make given more time.

07 Dos & Don'ts

Dos
  • Always ask for clarification — don't assume your assumption is correct.
  • Understand the real requirements before designing.
  • Think out loud — communicate constantly.
  • Suggest multiple approaches where relevant.
  • Once the blueprint is agreed, drill into the most critical component first.
  • Bounce ideas off the interviewer like a teammate.
  • Never give up.
Don'ts
  • Don't be unprepared for typical interview questions.
  • Don't jump to a solution before clarifying requirements.
  • Don't go deep on one component early — high-level first, then drill down.
  • Don't hesitate to ask for hints if stuck.
  • Don't think in silence.
  • Don't assume you're done once you've given a design — ask for feedback early and often.
