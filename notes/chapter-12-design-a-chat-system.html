01 Requirements

Both 1-on-1 and group chat, mobile and web, 50 million DAU, group chat capped at 100 members, text-only, messages under 100,000 characters, no end-to-end encryption for now, chat history stored forever.

"Chat app" hides real product diversity — one-on-one (Messenger), office group chat (Slack), large-group voice (Discord). Scoping which one matters more here than in most chapters.

02 The core protocol problem

ApproachMechanismProblem
PollingClient periodically asks "anything new?"Wasteful — most polls return no
Long pollingClient holds connection open until new data or timeoutSender/receiver may land on different servers; can't detect disconnects; inefficient for quiet users
WebSocketHTTP upgrades to a persistent, bidirectional connectionRequires careful server-side connection management

WebSocket actually inverts who can initiate — and that inversion is why the chat service, uniquely in this book, has to be genuinely stateful.

03 High-level design

Worth pausing on

Since Chapter 1, "keep the web tier stateless" has been close to a universal rule. The chat service is a genuine, structural exception — forced by WebSocket, not a lapse in discipline. A WebSocket connection is a real socket in one machine's memory; you can't load-balance individual messages the way you can plain HTTP requests.

04 The scalability reality check

Single-server connection memory

  1. 1,000,000 concurrent users × 10 KB/connection≈ 10 GB
The math checks out — the architecture still doesn't

A single server could genuinely hold this much connection memory. Yet single-server is still a red flag: SPOF, no scaling headroom, no maintenance without disconnecting everyone — none of which shows up in a capacity calculation. Back-of-envelope estimation tells you whether a quantity is feasible, not whether the architecture is sound.

05 Storage & message IDs

Chat history is a distinct workload: enormous volume (60 billion messages/day, Messenger+WhatsApp), strong recency bias but genuine random-access needs (search, jump-to-mention), and a read:write ratio ≈ 1:1 — notably different from the URL shortener's ~10:1 or the news feed's read-heavy skew.

Key-value stores win: easy horizontal scaling, low latency, and relational DBs handle the "long tail" poorly as indexes grow. Real-world proof: Messenger uses HBase, Discord uses Cassandra — the same Cassandra from Chapter 6's reference systems.

Message ID generation — three approaches
  • auto_increment — doesn't work on NoSQL (echoes Ch7's opening problem)
  • Global 64-bit sequence generator (Snowflake, Ch7) — fully solved, drop it in
  • Local sequence generator — unique only within a group/channel

Ordering only ever matters within one conversation. Before reaching for a fully-solved hard problem from an earlier chapter, check whether the requirement really needs global uniqueness, or just uniqueness within an already-bounded scope.

06 Service discovery

A regular load balancer decides fresh per request — a wrong pick costs little. Service discovery decides once per connection, sticking for hours — a bad pick isn't self-correcting. Zookeeper (centralized coordination) solves the same "which nodes are healthy" problem as Ch6's gossip protocol (decentralized) — chosen here because clients need one authoritative answer.

07 Message flows

Persistence happens independently of live delivery — same durability-first instinct as Ch6's write path and Ch10's notification log.

Multi-device sync

Each device tracks its own cur_max_message_id — a high-water mark. New = recipient matches and message ID > that mark. Works cheaply because message IDs are sortable by time, not just unique — sortability is what enables a single scalar bookmark instead of per-message tracking.

Small group chat flow

The parallel worth naming

Copying a message into every member's inbox on write is structurally identical to Chapter 11's fanout-on-write for news feeds — and has the exact same limitation: one write triggering N copies doesn't scale once N gets large. Explicitly why group size is capped at 100 here (WeChat caps at 500).

08 Online presence

Login/logout are simple status flips. Disconnection is the hard case — naive immediate-offline causes rapid flapping from ordinary network flicker.

offline after 30s silence
t=0s
t=5s
t=10s
t=40s: marked offline

Client heartbeats every 5s. Only after a full 30s of silence does the status actually flip — a debouncing pattern: don't react to one noisy signal, wait for it to persist. Same move as Ch6's gossip protocol requiring two independent sources before declaring a node down.

The scaling limit — third appearance of this pattern

Fine for small groups; a 100,000-member group's status change would generate 100,000 events. Fix: stop pushing for large groups — pull status only when a user enters the group or refreshes. Identical move to Chapter 11's fanout-on-read fix for celebrities. Whenever a write threatens to fan out to an unbounded number of consumers, the fix is never "push harder" — it's "stop pushing to the outliers, let them pull instead."

09 Wrap-up talking points

  • Media files — compression, cloud storage, thumbnails for photos/videos.
  • End-to-end encryption — only sender and recipient can read messages.
  • Client-side caching — reduces client/server data transfer.
  • Load time — Slack's Flannel: a geographically distributed edge cache.
  • Chat server failure — Zookeeper reassigns affected clients to a new server.
  • Message resend mechanism — retry and queueing, the same at-least-once pattern used throughout this book.
