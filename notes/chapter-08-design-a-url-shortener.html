01 Requirements

  • 100 million URLs generated per day.
  • Shortened URL should be as short as possible.
  • Allowed characters: 0-9, a-z, A-Z (62 characters).
  • Shortened URLs are never deleted or updated.

Two core use cases: shorten a long URL, and redirect a short URL back to the original.

02 Back-of-envelope estimation

QPS and storage

  1. Write QPS = 100,000,000 ÷ 86,400≈ 1,160
  2. Read QPS = 1,160 × 10 (10:1 ratio)= 11,600
  3. 10-yr records = 100M × 365 × 10= 365 billion
  4. Storage = 365 billion × 100 bytes≈ 36.5 TB
Errata caught while studying this chapter

The book states this comes out to 365 TB, but its own arithmetic (365 billion × 100 bytes) actually gives 36.5 TB. The 365 billion figure already includes the 10-year multiplier — multiplying by "10 years" again double-counts it, as if the service ran for 100 years. Worth independently re-deriving numbers rather than trusting a source at face value.

03 API design, and 301 vs. 302

  • POST api/v1/data/shorten — body {longUrl} → returns the short URL.
  • GET api/v1/shortUrl — returns the long URL for redirection.
301 (permanent)302 (temporary)
Browser cachingYes — later clicks skip your serversNo — every click hits your service
Server loadLowerHigher
AnalyticsPoor — only first click visibleGood — every click trackable

The tradeoff in one line: 301 optimizes for infrastructure cost; 302 optimizes for data. A product decision, not just a technical footnote.

04 Data model

The naive design keeps <shortURL, longURL> in an in-memory hash table — useless for 36+ TB of real data. The actual design stores this mapping in a relational database: a simple table of id, shortURL, longURL.

05 The hash function

Need the smallest n such that 62ⁿ ≥ 365 billion: 62⁶ isn't enough, 62⁷ ≈ 3.5 trillion is — so 7 characters.

Approach 1 — hash + collision resolution

Hash the long URL (CRC32/MD5/SHA-1), take the first 7 characters. Even the shortest (CRC32) needs truncating, which risks collisions. Resolve by recursively appending a predefined string and re-hashing until free. Cost: a DB lookup on every write to check for collisions — mitigated the same way as Chapter 6's read path, with a bloom filter.

Approach 2 — base 62 conversion (chosen)

Convert a globally unique integer ID (Chapter 7's ID generator) directly to base 62. Uniqueness is inherited structurally — no collisions possible, no DB check needed.

Worked example — 11157 to base 62

  1. 11157 = 2×62² + 55×62¹ + 59×62⁰= 7688+3410+59 ✓
  2. digits [2, 55, 59]map via 0-9→0-9, 10-35→a-z, 36-61→A-Z
  3. 2→'2', 55→'A'+19='T', 59→'A'+23='X'→ "2TX"
Hash + collision resolutionBase 62 conversion
Collisions possible?Yes — needs detection/resolutionNo — structural uniqueness
DB check per write?Yes (bloom filter helps)No
Extra dependencyNoneCh7's unique ID generator

Full circle: Chapter 7's ID generator exists largely so this chapter can use it here — base 62 avoids collision handling entirely by offloading uniqueness onto an already-solved problem.

07 Wrap-up talking points

  • Rate limiting (Ch4) — guards the shortening endpoint against abuse.
  • Web server scaling (Ch1) — stateless web tier, scale by adding/removing servers.
  • Database scaling (Ch1, 5, 6) — replication and sharding once one DB can't hold 36+ TB.
  • Analytics — a legitimate business reason to prefer 302 over 301.
  • Availability, consistency, reliability (Ch1) — general principles apply here too.

08 What back-of-envelope estimation tells an engineer

Prompted directly by catching the book's own 36.5 TB vs. 365 TB error above.

  1. It falsifies bad designs before you build them — the 36.5 TB number is what kills the "everything in a hash table" idea outright.
  2. It tells you where to spend engineering effort — the 10:1 read:write skew is why the redirect flow gets a cache and the shortening flow doesn't.
  3. It can directly derive a design parameter — "365 billion capacity" + "62 characters" mathematically produces "7-character codes."
  4. It's the guard against over-engineering in both directions — small numbers justify skipping this machinery entirely; big numbers earn the right to use it.
  5. It forces assumptions into the open — "100 bytes/URL," "10:1 ratio," "10 years" are assumptions, written down so they're checkable later.
  6. It's a check on your own reasoning — the 36.5 vs. 365 TB catch only happened because the calculation was written out step by step.
