Chapter 6 — Design a Key-Value Store

01 What a key-value store is

A non-relational database: each unique key maps to an opaque value (string, list, object). The design is scoped to exactly two operations — put(key, value), get(key) — no joins, no range queries, no secondary indexes. That narrow scope is what makes consistent hashing such a clean fit later: pure key→node routing is the entire access pattern.

Design goals

KV pairs < 10 KB · store big data · high availability · high scalability · automatic scaling · tunable consistency · low latency.

Single server: a hash table in memory — fast, but memory-bound. Compression and hot/cold splitting buy some headroom, but a single machine hits a hard ceiling on raw dataset size (a different trigger than the QPS-based scaling limits from earlier chapters) — which is what forces a distributed design.

02 CAP theorem

  • Consistency — every client sees the same data at the same time, regardless of node.
  • Availability — every request gets a response, even if some nodes are down.
  • Partition tolerance — the system keeps working despite a communication break between nodes.

A distributed system cannot fully guarantee all three at once.

The practical reframing: network partitions aren't optional — they will happen. So the real, practical question is: when a partition occurs, do you block to stay consistent, or keep serving and risk staleness? A CA system — sacrificing partition tolerance — cannot exist for a genuinely distributed system; it only works as long as nothing ever goes wrong.

The thread for the rest of the chapter: Dynamo and Cassandra choose AP. Every remaining topic either implements that choice, or cleans up the mess it creates.

03 Data partitioning

Same ring mechanism as Chapter 5. One addition here: heterogeneity — the number of virtual nodes a server gets is proportional to its capacity, so a beefier server owns proportionally more of the ring and takes proportionally more load.

Reminder

A virtual node isn't a separate running server — just an extra label/position on the ring resolving back to the same physical machine, purely to improve statistical fairness. Adding a physical server is never blocked by existing virtual nodes.

04 Data replication

Partitioning alone gives one owner per key — a single point of failure. Replication stores each key on N servers: walk clockwise from the key's position, pick the first N unique physical servers (deduped, since virtual nodes can make consecutive ring positions resolve to the same machine).

replica server other server key0

Cross-data-center placement: failures are often correlated (a power/network outage takes out a whole DC at once) — replicas are spread across physically distinct data centers, trading latency for real fault isolation.

Replication is asynchronous — a write doesn't need all N replicas to confirm before being "done." That raises the next question: how many of the N actually need to agree, and when?

05 Consistency — quorum consensus

  • N — number of replicas.
  • W — write quorum: a write succeeds once W replicas acknowledge it.
  • R — read quorum: a read succeeds once R replicas respond.
Misconception

W=1 does not mean data is written to one server — the write still goes toward all N replicas. It just means the coordinator only waits for the first ack before returning success.

The formula: W + R > N guarantees strong consistency — a pigeonhole argument. If a write only needs W acks, the fresh copy could sit on any W-sized subset of N. If a read needs R responses, it queries some R-sized subset. When W+R>N, those subsets are mathematically guaranteed to overlap by at least one replica.

N=3, W+R=4 > 3 → s1 is the guaranteed overlap, holding the fresh write. This is why N=3, W=R=2 is the commonly cited default.

What this tells a system architect

  1. Consistency becomes a per-workload dial, not a global binary property — the same machinery backs strong and loose paths, just via different N/W/R per key.
  2. It separates two concerns: N = fault tolerance/durability; W, R (relative to N) = latency/staleness tradeoff — independently tunable.
  3. It tells you where to pay the latency cost: read-heavy workloads want small R; write-heavy workloads want small W.
  4. It's a provable guarantee (pigeonhole), not a hand-wave — defensible with math, not just asserted.
  5. Bigger quorums expose you to tail latency — you wait for the slowest of R/W replicas, not the average. Part of why N=3,W=R=2 (the minimum satisfying the formula) beats maxing out "for safety."

06 Consistency models

  • Strong — any read returns the most recent write. Never stale.
  • Weak — a subsequent read may not reflect the most recent write.
  • Eventual — a specific case of weak: if writes stop, given enough time, all replicas converge.

Strong consistency is achieved by blocking a replica from new reads/writes until every replica agrees — literally W=N, R=N pushed to the extreme; the CP choice, made concrete. Dynamo and Cassandra default to eventual consistency instead, and so does this chapter.

Quorum settingConsistency model produced
W=N, R=N (full blocking)Strong, worst availability/latency
W+R>N, both <N (N=3,W=R=2)Strong, without needing every replica
W+R≤NWeak/eventual, best availability/latency
The crucial nuance

Eventual consistency does not mean "it fixes itself." It means if writes stop, replicas converge — it says nothing about concurrent writes, and the system does not automatically pick a winner among them. That's exactly what vector clocks exist for.

07 Inconsistency resolution — vector clocks

Why not timestamps? Server clocks drift — a genuinely later write can carry an earlier timestamp, so naive "last write wins" can silently lose data. Vector clocks use a logical clock — tracking who processed what, not when.

A vector clock is a paper trail: D([Sx,2],[Sy,1]) means "2 writes processed by Sx, 1 by Sy." Every write bumps only the handling server's own counter.

Case 1 — one server, no branching

D1 written by Sx        → D1 = [Sx:1]
D2 (edit of D1), by Sx   → D2 = [Sx:2]

2 ≥ 1 → clean descent. Only one lineage, nothing to branch from.

Case 2 — a second server joins, still sequential

D2 read, updated to D3, handled by Sy  → D3 = [Sx:2, Sy:1]

A server touching the lineage for the first time adds itself at 1, keeping what it inherited. General rule: Y descends from X if every one of Y's counters ≥ X's (missing = 0).

Case 3 — the actual fork

Two different clients read the same version D2=[Sx:2] at nearly the same time, before either writes back:

Client A → D3, handled by Sy  → D3 = [Sx:2, Sy:1]
Client B → D4, handled by Sz  → D4 = [Sx:2, Sz:1]

Check both directions: D3 descend from D4? Sz: 0≥1 fails. D4 descend from D3? Sy: 0≥1 fails. Neither direction passes — that double failure is the definition of a conflict.

Resolving the fork — the merge, and the client's role

  1. The read returns all siblings, not a silently-picked winner — every conflicting version plus its vector clock.
  2. The client merges the actual values using domain-specific logic — the vector clock only proves a conflict exists, never what the correct merge is.
  3. The client writes back the merge, passing the vector clocks ("context") of everything it merged — this is how it tells the server which versions this write supersedes.
  4. The server builds the new clock: max of each server's counter across all merged parents, then increment its own on top.
  5. Resolved: the new version dominates every former sibling, so future reads see a clean descendant.
Worked example — shopping cart 
D3 = {apple, banana}   clock [Sx:2, Sy:1]
D4 = {apple, cherry}   clock [Sx:2, Sz:1]

client reads both → merges via union → {apple, banana, cherry}
writes back with context = [D3's clock, D4's clock]
server (Sx): max(2,2)=2, max(1,0)=1, max(0,1)=1, +1 to itself
→ D5 = {apple, banana, cherry}, clock [Sx:3, Sy:1, Sz:1]

"Client" usually means the application layer, not necessarily a human — merges can be fully automatic, or for genuinely ambiguous data, surfaced to a person to choose.

Two real costs
  • The client must implement conflict-resolution logic — the store can detect a conflict but has no domain knowledge to resolve it.
  • Vector clocks can grow unboundedly as more servers touch a long-lived key — fixed by capping length and dropping the oldest entries (not a real problem in practice per the Dynamo paper).

What this tells an engineer

  1. Eventual consistency isn't free — this is where you see the bill: real conflict-resolution logic you must build and maintain.
  2. Never trust wall-clock time to order events across machines — use logical/causal ordering instead. This generalizes well beyond this chapter.
  3. The storage layer can detect a conflict; it can never resolve one for you — resolution is inherently domain-specific.
  4. Model data to be naturally mergeable (sets, counters, append-only logs — the idea behind CRDTs) rather than single ambiguous mutable fields.
  5. The general principle: push ambiguous decisions to the edges (client/app); keep the core storage system simple, fast, and available.

08 Handling failures — an escalation ladder

Failure detection — gossip protocol

A single node's claim that "X is down" needs independent corroboration. All-to-all multicasting works but doesn't scale (~n² messages). Gossip protocol instead:

  1. Each node keeps a membership list: {member_id → heartbeat_counter}.
  2. Each node periodically bumps its own heartbeat.
  3. Each node periodically gossips its list to a small set of random peers.
  4. Recipients merge the info, then gossip onward — spreading virally through the cluster.
  5. A heartbeat stale past a threshold → marked offline, and that news spreads the same way.

Temporary failures — sloppy quorum + hinted handoff

Strictly requiring the literal N designated replicas would stall requests if one is down — undermining the AP choice. Sloppy quorum: take the first W/R healthy servers on the ring, skipping any marked down. Hinted handoff: a healthy stand-in remembers the data really belongs elsewhere, and hands it back once the original recovers.

Permanent failures — anti-entropy via Merkle trees

If a node never comes back (or replicas silently drift without ever being flagged down), a periodic anti-entropy check is needed. Comparing every key directly is too expensive at scale; one big hash for the whole dataset is cheap but tells you nothing about where a mismatch is.

Merkle tree — hierarchical hashing to localize the difference: divide the key space into buckets → hash each key → one hash per bucket → build upward to a single root hash.

Comparison protocol: compare roots first — match means identical, done in one comparison. On mismatch, recurse into children, discarding any branch whose hash matches (cleared, never inspected further), until the differing bucket(s) are isolated.

Cost scales with the difference between replicas, not dataset size. Book's real config: ~1 million buckets per 1 billion keys (~1,000 keys/bucket) — localizing a divergence costs ~20 hash comparisons plus scanning one bucket, not a billion keys.

Bucket size is a real tradeoff

One leaf per key = maximum precision but a huge tree to store. Bigger buckets = smaller tree, more scanning once localized. Once a differing key is found, if both replicas hold genuinely different values (not just one missing), the same vector-clock ancestor/conflict logic from topic 7 can decide how to reconcile it.

Data center outage

Not new mechanism — the payoff of replicating across physically distinct data centers (topic 4). A whole DC going dark still leaves other DCs serving live replicas.

The full ladder: gossip detects → sloppy quorum + hinted handoff routes around a temporary absence → Merkle-tree anti-entropy repairs permanent/silent drift → cross-DC replication survives a whole building going dark.

09 Architecture, write path, read path

  • Clients only see get/put.
  • A coordinator proxies between client and storage nodes.
  • Nodes sit on the consistent-hashing ring; each key lives on N of them.
  • Every node runs identical responsibilities — any node can coordinate, gossip, or hold replica data. No master, no distinguishing SPOF — a deliberate contrast to Chapter 1's master-slave replication.

Write path

Commit log first, purely for durability — and it's a cheap sequential disk write (Chapter 2: sequential beats random access). Writes land in memory rather than a sorted on-disk structure directly, because updating that on every write means constant random disk seeks — exactly what Chapter 2 says to avoid. This pattern (commit log + memtable + SSTable) is a named design: the LSM-tree, used by Cassandra, RocksDB, LevelDB.

Read path

A bloom filter is far smaller in memory than an exact per-SSTable key index. It can say "definitely not here" (skip) or "might be here" (check) — never a false negative, sometimes a false positive. That asymmetry is the safe direction to be wrong in: worst case, wasted work; never a silently-missed key that actually exists.

The full arc, end to end

CAP theorem forces the AP choice → consistent hashing partitions the data → replication gives redundancy → quorum consensus tunes latency/consistency per workload → consistency models describe the guarantee produced → vector clocks detect (never resolve) the conflicts AP allows → gossip / sloppy quorum+hinted handoff / Merkle trees escalate from momentary blips to permanent loss to whole-datacenter outages → the write/read path is how one node stores and retrieves data efficiently underneath all of it.
