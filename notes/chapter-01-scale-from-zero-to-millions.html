Chapter 1 — Scale From Zero to Millions of Users

Everything starts on one server. This chapter grows it, tier by tier, into an architecture built for millions — each addition below exists to fix a specific failure the previous stage introduced.

01 Single server setup

Everything — web app, database, cache — runs on one machine. Simple, and the natural place to start.

Traffic sources:

  • Web app — server-side code (Java, Python …) handles logic and storage; client-side HTML/JS handles presentation.
  • Mobile app — talks HTTP to the server; JSON is the typical response format.

02 Separate the database out

One server becomes two — a web tier and a data tier — so each can scale independently.

Relational (SQL / RDBMS)Non-relational (NoSQL)
ExamplesMySQL, PostgreSQL, OracleDynamoDB, Cassandra, HBase, CouchDB, Neo4j
StructureTables + rows, supports joinsKey-value, document, column, graph — joins generally unsupported
Default choiceYes — 40+ years mature, well understoodReach for it when SQL doesn't fit
Reach for NoSQL when
  • The application requires super-low latency.
  • Data is unstructured, or has no relational structure.
  • You only need to (de)serialize data — JSON, XML, YAML.
  • You need to store a massive volume of data.

03 Vertical vs horizontal scaling

  • Vertical scaling ("scale up") — add more CPU/RAM to one machine. Simple, but:
    • Hits a hard hardware ceiling.
    • No failover or redundancy — one box dying takes the whole app down.
  • Horizontal scaling ("scale out") — add more machines. Preferred at scale.

04 Load balancer

Distributes incoming traffic across a pool of web servers. Users hit the load balancer's public IP; it talks to backend servers over private IPs, unreachable from the internet.

Solves two problems at once:

  • Failover — if server 1 dies, traffic reroutes to server 2; a healthy replacement is added back to the pool.
  • Scale — growing traffic just means adding more servers behind the load balancer.

05 Database replication

Master handles writes (insert / update / delete). Slaves copy data from the master and serve reads only — usually many more slaves than masters, since read:write ratios skew heavily toward reads.

Benefits: better performance (reads and writes are parallelized across nodes), reliability (data survives a single node/data-center disaster), high availability (the app stays up even if one DB node is offline).

Failure handling
  • Slave goes down → reads temporarily shift to the master (or another healthy slave) until a replacement slave is provisioned.
  • Master goes down → a slave is promoted to master. Tricky in practice: the promoted slave's data may be stale, so recovery scripts patch the gap. Multi-master and circular replication exist, but are more complex setups.

06 Cache

A fast, temporary, in-memory store for expensive or frequently-requested responses, sitting between the web tier and the database.

Design considerations

  • When to use — best for read-heavy, write-light data. Cache is volatile (a restart wipes it), so never treat it as the source of truth.
  • Expiration policy — too short thrashes the DB with reloads; too long serves stale data.
  • Consistency — cache and DB writes aren't in one transaction, so they can drift, especially across regions (see Facebook's Scaling Memcache paper).
  • Avoiding SPOF — a single cache node is a single point of failure; run several across data centers, and overprovision memory as a buffer.
  • Eviction policy — once full: LRU is most common; LFU and FIFO are alternatives.

07 Content delivery network (CDN)

Geographically distributed servers caching static content — images, JS, CSS, video. The closer the edge server, the faster the load.

Considerations
  • Cost — you pay for data transfer; don't cache rarely-used assets.
  • Cache expiry — same too-long / too-short trade-off as regular caching.
  • CDN fallback — detect outages and fall back to the origin.
  • Invalidation — call the vendor's invalidation API, or use object versioning, e.g. image.png?v=2, to force a fresh fetch.

08 Stateless web tier

Stateful servers remember client data (like a session) between requests, which forces sticky sessions — every request from a user must reach the same server — adding load-balancer overhead and complicating scaling and failure handling.

Stateless servers hold no session state themselves; it moves to a shared data store (relational DB, Redis/Memcached, or NoSQL — NoSQL is common here for easy scaling).

Payoff: any server can handle any request, which makes robust autoscaling — adding or removing web servers automatically based on load — straightforward.

09 Multiple data centers

Once traffic is international, a single data center isn't enough for availability or latency.

If DC2 goes down, geoDNS routes 100% of traffic to DC1 — assuming data is kept in sync.

Challenges to solve

  • Traffic redirection — geoDNS routes users to the nearest healthy data center.
  • Data synchronization — a failover could route users to a data center missing their data. Common fix: replicate data across data centers (e.g. Netflix's async multi-DC replication).
  • Test & deployment — automated, consistent deployment across every data center.

10 Message queue

A durable component enabling asynchronous communication and decoupling. Producers publish messages; consumers read and act on them — neither needs the other online at the same moment, and each scales independently.

Example: photo customization — crop, sharpen, blur. Web servers publish jobs to the queue; workers pull and process them asynchronously. Queue backing up → add workers; queue mostly empty → scale workers down.

11 Logging, metrics, automation

Not critical for a small site — essential once the business is large.

  • Logging — monitor error logs per-server, or aggregate them centrally for easier search and analysis.
  • Metrics —
    • Host-level: CPU, memory, disk I/O.
    • Aggregated: performance of the whole DB tier, cache tier, etc.
    • Business: DAU, retention, revenue.
  • Automation — CI verifies every check-in; automated build/test/deploy pipelines catch problems early and boost productivity.

12 Database scaling

Vertical scaling

A bigger single DB server — AWS RDS offers instances with up to 24 TB of RAM. Sometimes sufficient: Stack Overflow ran on one master DB in 2013 with 10M+ monthly uniques. Drawbacks: a hardware ceiling, a bigger single-point-of-failure risk, and high cost.

Horizontal scaling — sharding

Split one large database into smaller shards, each holding a unique slice of the data but sharing the same schema. A hash function on the sharding key (partition key) routes each query to the right shard.

The most important property of a sharding key: it should distribute data evenly across shards.

New problems sharding introduces
  • Resharding — needed when a shard fills up, or uneven distribution causes "shard exhaustion" faster on some shards. Requires changing the hash function and moving data; consistent hashing (Chapter 5) is the standard fix.
  • Celebrity / hotspot key problem — heavy access concentrated on one shard (e.g. several celebrities' data landing on the same shard) overloads it. Fix: dedicate a shard per hot key, and partition further if needed.
  • Joins & denormalization — cross-shard joins are hard or impossible; the common workaround is denormalizing so a query only needs a single table.

Summary checklist

How we scaled a single server to serve millions of users:

  • ✓ Keep the web tier stateless
  • ✓ Build redundancy at every tier
  • ✓ Cache data as much as possible
  • ✓ Support multiple data centers
  • ✓ Host static assets on a CDN
  • ✓ Scale the data tier by sharding
  • ✓ Split tiers into individual services
  • ✓ Monitor the system and automate
