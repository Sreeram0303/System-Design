01 Notification types & requirements

Supports push/SMS/email; a soft real-time system (fast preferred, slight delay under heavy load acceptable); iOS, Android, desktop; triggered by client apps or scheduled server-side; users can opt out. Volume: 10M push, 1M SMS, 5M emails per day.

SMS—Twilio, Nexmo

Worth noticing immediately

Every delivery path routes through a third-party service outside your control. A large chunk of the real reliability risk lives outside the system entirely — which is why extensibility (plugging/unplugging a provider without a redesign) matters here specifically, and why "a provider might be unavailable in some market" (FCM doesn't work in China; Jpush/PushY fill in) is a first-class concern.

02 Contact info gathering flow

On signup/install, API servers collect contact info. Email/phone live in the user table; device tokens live in a separate device table since a user can have multiple devices.

Consequence: "send a notification to a user" can mean fanning out to several device tokens at once, not just one.

04 Improved design — decoupling the pipeline

Why separate queues per type

If FCM has an outage, only the Android queue backs up — SMS and email keep draining normally. A single shared queue would turn one third-party outage into a systemic one.

The 6-step flow

1. A service calls the notification server's API
2. Notification server fetches user info, device token, settings from cache/DB
3. The event is pushed to the correct queue (e.g., iOS push → iOS PN queue)
4. Workers pull events from their queue
5. Workers call the corresponding third-party service
6. The third-party service delivers to the actual device

The notification server's job ends at step 3 — it never waits on a third-party response. Slow, unpredictable third-party latency is isolated to the workers.

05 Reliability

Preventing data loss

Hard requirement: delayed or reordered is fine, lost is not. Fix: persist to a notification log database as part of the send, plus a retry mechanism — the same durability-first instinct as Chapter 6's write path.

Exactly-once delivery doesn't exist

If an ack never arrives, the worker can't tell "never delivered" from "delivered fine, ack lost." The only safe move is to retry — which risks a duplicate if it was actually the second case.

The two honest baseline choices

At-most-once: never retry on ambiguity — no duplicates, but risk losing messages. At-least-once: always retry — never lose, but risk duplicates. The requirement ("never lost") picks at-least-once, plus a dedup layer (check event ID: seen before → discard, new → send) — same shape as Chapter 9's "Content Seen?"/"URL Seen?".

The pattern worth naming

Same move as Chapter 6's eventual consistency: don't prevent an imperfection outright (lost writes there, lost notifications here) — pick a simple, robust base guarantee that allows a specific, bounded imperfection (staleness there, duplicates here), then bolt on a thin reconciliation layer (vector clocks there, event-ID dedup here) to clean it up afterward.

06 Additional components

Templates

Avoid rebuilding millions of similar notifications from scratch — consistent format, fewer errors, faster to produce.

Notification settings

{user_id, channel, opt_in} — check the specific channel's opt-in before sending anything.

Rate limiting

Ch4's rate limiter, inverted — protects the user from too many notifications from your own services, not the server from clients.

Retry mechanism

Failed sends return to the queue; persistent failure alerts developers instead of retrying silently forever.

Security

appKey/appSecret authenticate which clients can call the push APIs at all.

Queue monitoring

Growing queue depth = workers can't keep up = add more. The runtime counterpart to the design-time QPS estimate.

Events tracking

Open rate, click rate, engagement — tells you whether targeting/rate limiting is actually working.

07 Wrap-up

The final design layers authentication and rate-limiting onto the notification servers, adds a retry mechanism, uses templates for consistent creation, and adds monitoring/tracking for health and future tuning.

  • Reliability — a robust retry mechanism minimizes failure rate.
  • Security — appKey/appSecret ensure only verified clients send notifications.
  • Tracking & monitoring — implemented at every stage to capture important stats.
  • Respect user settings — check opt-in before sending, always.
  • Rate limiting — frequency capping users will actually appreciate.
