01 Requirements — the exact example from Chapter 3

  • Both mobile and web.
  • Core features: make a post, see friends' feed.
  • Reverse-chronological, not ranked — no scoring/ML subsystem needed.
  • 5,000 max friends — bounded, not unlimited followers.
  • 10 million DAU.
  • Feed contains images and video, not just text.

The friend-count number isn't a "scale" question — it's a fan-out shape question. It determines whether pushing a post to every friend's feed at write time is cheap and bounded. A hard cap of 5,000 looks safe at a glance — topic 5 revisits whether it actually is.

05 Fanout deep dive — the payoff of Chapter 3's fan-out question

Fanout = delivering a post to all of a user's friends.

Fanout on write (push)

Pre-compute the feed at write time — a post is pushed directly into every friend's cache immediately.

  • Pro: real-time delivery, fast reads
  • Con: the "hotkey problem" for users with many friends
  • Con: wasted work pre-computing for inactive users
Fanout on read (pull)

Assemble the feed on demand — recent posts pulled from friends only when the home page loads.

  • Pro: no wasted work on inactive users
  • Pro: no hotkey problem
  • Con: reads become slow — assembled live every time

The answer: push for the majority of users (fast reads matter most for typical accounts); pull for celebrities/high-follower accounts. Consistent hashing (Ch5) distributes whatever fanout load still needs to happen more evenly across shards.

Worth being precise

5,000 max friends is bounded, but the deep dive still flags a hotkey problem — "bounded" doesn't mean "small enough to ignore." Same lesson as Chapter 9's politeness problem in a different costume: an aggregate budget needs explicit protection from any single outlier, and a cap alone doesn't remove that need.

06 The fanout service, step by step

  1. Fetch friend IDs from a graph database — purpose-built for relationship data.
  2. Filter by settings — muted friends or selectively-hidden posts drop out here, before fanning out.
  3. Send the friends list + post ID to a message queue — never processed inline with the publish request (Ch1's message queue lesson).
  4. Fanout workers pull from the queue and write into the newsfeed cache.
  5. Only IDs are stored, never full objects — a configurable per-user size limit keeps the cache small.

07 Retrieval & hydration

Media (images/video) is served from a CDN — the same reasoning as Chapter 1's CDN section.

Hydration is a tradeoff, not a free lunch

Storing only IDs keeps the newsfeed cache small and cheap — but retrieval now needs an extra assembly step to make it renderable. The same shape as Chapter 6's bloom filter needing a follow-up check, or Chapter 8's base-62 code needing a DB lookup for the real long URL: cheap to store rarely comes free, the cost usually just moves to whoever reads it back.

08 Cache architecture — five layers, not one

News Feed<post_id, user_id> IDsVery read-heavy, tiny entries, critical path

Social GraphFriend/follow relationshipsRead-heavy, changes rarely
ActionLikes/replies on a postFrequent writes and reads
CountersLike/reply/follower countsExtremely high write volume vs. entry size

Same instinct as Chapter 1's separate tiers and Chapter 10's per-type queues — bundling genuinely different access patterns into one shared cache means none of them can be tuned or scaled independently.

09 Wrap-up — scaling talking points

  • Database scaling — vertical vs. horizontal, SQL vs. NoSQL, master-slave replication, read replicas, consistency models, sharding.
  • Keep the web tier stateless.
  • Cache data as much as possible.
  • Support multiple data centers.
  • Decouple components with message queues.
  • Monitor key metrics — peak-hour QPS, feed-refresh latency.

Every one of these is a direct callback to a chapter already covered — this chapter's contribution isn't new vocabulary, it's showing how all of it comes together to solve one concrete, familiar product.
