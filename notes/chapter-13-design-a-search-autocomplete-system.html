01 Requirements & estimation

Prefix matching only, top 5 suggestions ranked by popularity, no spell check, English/lowercase only for now, 10 million DAU. Facebook's own autocomplete targets under 100ms, or it visibly stutters.

QPS

  1. ~20 requests per completed query (one per keystroke)e.g. "dinner" → 6 requests
  2. 10M users × 10 queries/day × 20 chars ÷ 86,400s≈ 24,000 QPS
  3. Peak QPS = 24,000 × 2≈ 48,000

The "20 requests per query" figure is self-inflicted by the UX itself — exactly why sub-100ms latency is non-negotiable, not just a nice target.

02 Naive high-level design

SELECT query FROM table
WHERE query LIKE 'tw%'
ORDER BY frequency DESC LIMIT 5

A deliberate strawman — real-time per-keystroke writes don't scale, and a LIKE scan doesn't stay fast as the table grows. Two separate weaknesses, two separate fixes ahead.

03 Trie data structure, and the naive algorithm

1. Find the prefix node          — O(p)
2. Traverse subtree for children — O(c)
3. Sort children, take top k     — O(c log c)

Worked example: k=2, prefix "tr" → subtree yields [tree:10],[true:35],[try:29] → sorted top 2: [true:35],[try:29].

The same prefix gets queried repeatedly while the underlying data barely changes between requests — re-sorting every time recomputes an answer that was already computed moments ago.

04 Two optimizations — down to O(1)

OptimizationEffect
Limit max prefix length (~50)Find prefix: O(p) → O(1)
Cache top-k at every nodeReturn top-k: O(c log c) → O(1)
What this actually is

Pre-compute the expensive answer at build time so query time is a trivial lookup — the same move as Chapter 11's fanout-on-write and Chapter 6's write path, here showing up at the algorithmic/data-structure level rather than the infrastructure level.

05 Data gathering pipeline

Accumulation vs. replace — resolving an ambiguity

Aggregated Data accumulates one row per query per week, forever — not overwritten. Workers sum a query's full weekly history (40 + 2 this week = 42) to compute its current total, then bake that into the new trie. "Replace the old trie" means swapping the finished tree object atomically — not discarding accumulated counts. Open question the book leaves unresolved: sum over all time, or a rolling/decaying window? That tension is exactly why real-time trending (topic 10) is hard here.

Distinct from the buffer-then-flush pattern (Ch1/6/9): that pattern accumulates writes incrementally. This pipeline rebuilds the whole trie from scratch and replaces it wholesale — same instinct, different mechanism.

07 Query service

1. Query → Load Balancer → API servers
2. API servers fetch from Trie Cache
3. Cache miss → replenish from Trie DB

Same cache-aside, read-through pattern as Ch1, Ch6, and Ch8.

  • AJAX — every keystroke's request is async; with ~20 requests/query, this is what makes search-as-you-type physically viable in a browser.
  • Browser caching — Google's real header: Cache-Control: private, max-age=3600. private = for one user only, never cached by a shared intermediary.
  • Data sampling — log 1-in-N requests. Safe because ranking only needs relative popularity, not exact counts — a different tradeoff flavor than most of this book (accuracy for cost, not space or latency).

08 Trie operations

Update — a cost topic 4 didn't mention

Updating one node forces updating every ancestor up to the root, since ancestors cache their descendants' top-k. The earlier "space for time" framing was incomplete — the real tradeoff is space and update cost, for read speed. In-place updates are only acceptable if the trie is small enough that the cascade stays cheap; otherwise, rebuild weekly and replace wholesale.

Delete — a two-layer moderation design

A filter layer in front of the Trie Cache removes bad suggestions immediately at serving time; the underlying data is also removed from the DB asynchronously, so the next rebuild excludes it at the source too. Same combination-move as Ch10's at-least-once + async dedup: fast reactive fix now, slower structural correction later.

09 Scaling the storage

Naive: shard by first letter (a-m/n-z, up to 26 servers, then second-character sub-sharding beyond that).

Same symptom as Ch5, genuinely different cause

Consistent hashing's imbalance comes from randomness in hash placement — fixed with virtual nodes, because the data is assumed uniform. Here, far more English words start with 'c' than 'x' — the keyspace itself is permanently, predictably lumpy. Virtual nodes wouldn't help at all; the problem was never about server placement.

Fix: a shard map manager — group letters into shards by measured historical load, not alphabet range (e.g., 's' alone ≈ 'u' through 'z' combined → two shards, unequal in size, balanced in load). An explicit lookup table, recomputed as patterns shift.

A distinct sharding tool worth keeping alongside consistent hashing: when a key's skew is known rather than random, a data-driven lookup table can outperform a purely algorithmic hash-based approach.

10 Wrap-up — follow-up questions

  • Multi-language — store Unicode in trie nodes instead of assuming ASCII.
  • Per-country top queries — separate tries per region, stored in CDNs for speed.
  • Real-time trending — the original design breaks: weekly rebuilds are too slow and too infrequent. Only sketched: shard down the working set, weight recent queries more, and recognize trending data often arrives as continuous streams needing different tools entirely (Hadoop, Spark Streaming, Storm, Kafka) — each its own domain, out of scope here.
