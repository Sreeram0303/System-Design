Chapter 5 — Design Consistent Hashing

Plain hash(key) % N falls apart the moment a server joins or leaves — nearly every key changes owner. Bending the hash space into a ring, and walking it clockwise, fixes that.

"Consistent hashing is a special kind of hashing such that when a hash table is re-sized, only k/n keys need to be remapped on average — where k is the number of keys and n is the number of slots. In most traditional hash tables, a change in the number of slots causes nearly all keys to be remapped." Wikipedia, via Karger et al., MIT

01 The rehashing problem

Naive load balancing with N cache servers:

serverIndex = hash(key) % N

Fine while N is fixed. But take one server offline and N changes — nearly every key's hash(key) % N result changes with it, not just the keys that lived on the departed server. The result is a storm of cache misses across the entire system.

Illustrative distribution — the shape of the problem, not the book's exact hash outputs: removing one server out of four reshuffles most of the table, far more than the one server's worth of keys that actually needs to move.

02 Consistent hashing & the hash ring

Take a hash function with a huge output range (SHA-1: 0 to 2¹⁶⁰−1) and join its two ends — the range becomes a ring where values wrap around. Servers are hashed onto the ring by IP/name; keys are hashed onto the same ring, with no modular operation this time.

Server lookup: starting from a key's position, walk clockwise until you hit a server — that server owns the key.

server key dashed line — clockwise walk to owning server
The key insight

A server and a key get their position on the ring independently, from hashing their own identity — a key is never "placed on" a server directly. Ownership is purely the outcome of the clockwise-walk rule. This is what makes add/remove cheap: a key's own position never moves, so changing the server set only changes which server you hit first for keys in one specific arc.

Implementation detail: what "clockwise" compiles to

The ring is circular, so past the maximum hash value you wrap back to 0. In code, server hashes live in a sorted structure (sorted array, or a balanced BST / TreeMap); a lookup is a binary search for the smallest server hash ≥ the key's hash — O(log n). If nothing is found (key's hash is larger than every server's), the owner is simply the server with the smallest hash — that's the wraparound, expressed as an index wraparound instead of a geometric one.

03 Adding & removing a server

This is the entire payoff of the ring: changing the server set only touches a small, localized arc of keys — never the whole table.

  • Add a server: walk counter-clockwise from the new server to the previous one — every key in that arc moves to the new server. Everything else is untouched.
  • Remove a server: walk counter-clockwise from the removed server to the previous one — every key in that arc moves to the next server clockwise. Everything else is untouched.

04 Two problems with the basic ring

The basic algorithm (Karger et al., MIT) — hash servers and keys uniformly onto the ring, resolve clockwise — has two failure modes once servers are added or removed a few times:

  1. Uneven partition sizes. A partition is the arc between two adjacent servers. Random placement can leave one server's partition several times larger than its neighbors'.
  2. Non-uniform key distribution. In the extreme, one server can end up owning most of the ring while others sit nearly empty — the same hotspot/celebrity problem sharding already had (Chapter 1).

05 Virtual nodes — the fix

Represent each physical server with many points on the ring — virtual nodes / replicas — instead of just one. Lookup is unchanged: walk clockwise to the first virtual node, then resolve it to its physical server.

More virtual nodes → each physical server's ownership is chopped into many small, scattered slivers instead of one contiguous block, which evens out the total. This is a statistical effect: standard deviation shrinks as the virtual-node count grows — roughly ≈10% of the mean at ~100 virtual nodes, ≈5% at ~200 (per an independent experiment).

Tradeoff

More virtual nodes = more metadata to store and maintain. Tune the count to fit the system's needs rather than maximizing it blindly.

· What "only a fraction moves" really means

When a server is removed, the keys that move are exactly the ones it owned — the arc between it and the previous server. Not a random ~1/n sample; a specific, contiguous set.

Whether that fraction is close to 1/n (the formal "k/n keys" claim) isn't guaranteed by the basic ring — it depends on how much of the ring that server happened to own. Without virtual nodes, one server could hold a wildly disproportionate share, so removing it could move way more or less than 1/n of the data. Virtual nodes make each physical server's total share converge toward 1/n, which is what makes the formal claim hold in practice.

Contrast with naive hash % N: removing one server there reshuffles nearly every key, because N itself changes for keys that had nothing to do with the removed server. In consistent hashing, unaffected keys are structurally untouched — their clockwise walk never passed through the removed server's position.

What consistent hashing does not solve

An easy gap to miss: consistent hashing is purely a routing/partitioning primitive. It answers "which server is responsible for this key, right now" — it says nothing about how the actual data gets there. That depends on what's behind the ring:

Ring routes to a cache

Nothing needs to move at all — the database is still the source of truth. A dead server's keys simply cache-miss on their next request, fall through to the DB, and get cached fresh on the new owning server. "Redistributing keys" just means which server will miss next — that's why minimizing the remapped fraction matters: each remapped key is one cache miss hitting the DB. No data-loss risk, since the cache was never authoritative.

Ring routes to a real data store (Dynamo, Cassandra)

Losing a server's only copy would be real data loss, so the ring is paired with replication: each key lives on the ring-assigned server and the next N-1 servers clockwise (a "preference list"). A dead server's surviving replicas keep serving immediately; in the background, the system copies the under-replicated range onto the new Nth replica. Transient failures often use hinted handoff — a neighbor temporarily accepts writes until the original server returns.

The clean way to carry this forward: consistent hashing gives you the ring — a stable answer to "which node." What lives at each node, and how it survives that node dying, is a separate layer covered in Chapter 6 (Design a Key-Value Store).

06 Wrap-up

Benefits of consistent hashing:

  • Minimizes key redistribution when servers are added or removed.
  • Makes horizontal scaling easy — data stays evenly distributed.
  • Mitigates the hotspot/celebrity-key problem by spreading data more evenly across the ring.
Used in production by
  • Amazon Dynamo's partitioning component
  • Apache Cassandra's cluster data partitioning
  • Discord
  • Akamai's CDN
  • Google's Maglev network load balancer
