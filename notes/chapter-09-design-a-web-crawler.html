01 Requirements

Scoped to search engine indexing: 1 billion pages/month, HTML only, must catch new and edited pages, store crawled HTML for 5 years, ignore duplicate content.

Four qualities of a good crawler
  • Scalability — the web is huge, needs heavy parallelization
  • Robustness — malformed HTML, dead servers, malicious links are all routine
  • Politeness — never hammer one host with too many requests at once
  • Extensibility — new content types shouldn't require a redesign

02 Back-of-envelope estimation

QPS and 5-year storage

  1. QPS = 1B pages ÷ 30d ÷ 24h ÷ 3600s≈ 400 pages/sec
  2. Peak QPS = 2 × 400= 800
  3. Monthly storage = 1B × 500 KB avg page= 500 TB
  4. 5-yr storage = 500 TB × 12 × 5= 30 PB

Verified — unlike Chapter 8's storage calculation, this one checks out with no double-counting. Worth confirming every time, regardless of which way it turns out.

04 DFS vs. BFS

The web is a directed graph — pages are nodes, hyperlinks are edges. DFS can go arbitrarily deep down one path, risking narrow coverage. BFS (FIFO queue) is standard, but naive BFS has two problems:

ProblemWhy it happens
ImpolitenessMost links on a page point back to the same host — parallel BFS can burst-fire requests at one server, looking like a DoS attack
No prioritizationA random forum post mentioning "Apple" gets equal priority to apple.com's homepage

Both point at the same missing piece: a smarter queue between "discovered" and "downloaded" — the URL Frontier.

05 URL Frontier deep dive

Politeness, worked through

10,000 URLs from wikipedia.org, 200 from nytimes.com, 5 from a small blog:

No matter whether b1 holds 10 or 10 million URLs, exactly one worker pulls from it — Wikipedia's crawl rate is capped by W1's pace, completely decoupled from its backlog size.

Connects to a broader lesson

An aggregate capacity number (our 400-800 QPS) is a total system budget — it says nothing about fair allocation among whoever draws from it. Politeness prevents one host from monopolizing that budget, the same way Chapter 4's rate limiter prevents one client from monopolizing an API's budget. Same problem shape, different key.

Priority, worked through

apple.com/ scores 9, Wikipedia's Apple article scores 7, a forum post scores 2 — routed into priority-banded front queues f1 (8-10), f2 (4-7), f3 (0-3). The queue selector picks randomly, biased toward higher priority (~60/30/10%) — never a strict drain-f1-first rule, which would let f3 starve forever.

Front + back queues combined — tracing one URL

Priority determines how soon a URL enters the politeness system — it never lets a URL bypass its host's per-host throttle entirely.

Freshness

nytimes.com/ updates every few minutes → recrawled every 5-10 minutes. A static blog page → recrawled every few months. Two independent, reinforcing signals: update history and priority.

Frontier storage, worked through

Why a hybrid buffer is needed

  1. 500M URLs × ~150 bytes/entry≈ 75 GB metadata
  2. Enqueue rate: 400-800 pages/sec × dozens of links each≈ thousands of URLs/sec
  3. Individual disk writes at that rate (10ms/seek, Ch2)→ disk becomes the bottleneck

Fix: in-memory buffer absorbs enqueue/dequeue traffic, periodically flushed to disk as one large sequential write.

The recurring pattern across this book

WhereFast/hot layerDurable/bulk layer
Ch1 — single-server KV storeIn-memory hot dataDisk
Ch6 — LSM-tree write pathMemtable + commit logImmutable SSTable
Ch9 — Content StorageCache of popular pagesDisk (bulk HTML)
Ch9 — URL Frontier storageEnqueue/dequeue bufferDisk (bulk URLs)

One underlying trick, four layers: buffer frequent small operations in memory, batch them into large sequential disk writes. Expect it again anywhere "too big for memory, too slow for disk alone" shows up.

06 HTML Downloader

Robots.txt

Check and obey it before crawling any site. Real example (Amazon):

User-agent: Googlebot
Disallow: /creatorhub/*
Disallow: /rss/people/*/reviews

Cache it rather than re-fetching on every request to that host.

Performance optimizations

  • Distributed crawl — partition the URL space across servers/threads (Ch1's horizontal scaling); previews consistent hashing (Ch5) for that partitioning.
  • Cache the DNS Resolver — lookups are synchronous and slow (10-200ms, Ch2's latency table) and block the thread; cache domain→IP, refresh via cron.
  • Locality — place crawl servers, caches, queues, and storage close to the hosts being crawled (Ch1's CDN/multi-DC logic, reapplied).
  • Short timeout — cap wait time on unresponsive servers so one dead host doesn't quietly stall a worker thread.

08 Detecting problematic content

  • Redundant content — ~30% of pages are duplicates; hashes/checksums detect it (same mechanism as "Content Seen?").
  • Spider traps — infinite page structures, e.g. /foo/bar/foo/bar/.... Mitigated with a max URL length; no fully general automated fix exists — an unusually large discovered-page count on one site is the tell, often needing manual review.
  • Data noise — ads, code snippets, spam URLs excluded where possible.

09 Wrap-up talking points

  • Server-side rendering — JS/AJAX-generated links are invisible to raw HTML parsing; render the page first.
  • Filter unwanted pages — an anti-spam component given finite crawl resources.
  • Database replication and sharding (Ch1, 5, 6) — for data-layer availability/scalability.
  • Horizontal scaling — hundreds/thousands of stateless servers for large-scale crawls.
  • Availability, consistency, reliability (Ch1) — general principles apply here too.
  • Analytics — collecting/analyzing crawl data to keep tuning the system.
