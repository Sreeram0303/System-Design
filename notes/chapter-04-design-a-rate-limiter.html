Chapter 4 — Design a Rate Limiter

Controls how much traffic a client can send in a window. Five algorithms trade off memory, accuracy, and burst tolerance differently — and running one correctly across many servers is its own problem.

01 Why rate limit

A rate limiter caps how many requests a client or service can send in a period; excess calls are blocked. E.g. "max 2 posts/second," "max 10 accounts/day per IP," "max 5 reward claims/week per device."

  • Prevent DoS-style resource starvation — Twitter caps tweets at 300/3h; Google Docs API caps reads at 300/user/60s.
  • Reduce cost — fewer servers, and essential when paying per-call for third-party APIs.
  • Prevent server overload — filters excess traffic from bots or misbehaving clients.

02 Requirements

Scoped as a server-side API rate limiter, flexible enough to throttle by IP, user ID, or other properties, built for large scale, and working in a distributed environment.

  • Accurately limit excessive requests.
  • Low latency — must not slow down HTTP responses.
  • Minimal memory use.
  • Works across multiple servers/processes.
  • Clear exceptions shown to throttled users.
  • High fault tolerance — a dead cache node shouldn't take the rest of the system down.

03 High-level design

Client-side enforcement is unreliable — requests can be forged and clients aren't fully under your control. Server-side, either baked into the API server or as dedicated middleware, is the standard. At larger scale this middleware is often an API gateway — also handling SSL termination, auth, IP whitelisting.

Server-side vs. gateway — depends on
  • Whether your stack can implement rate limiting efficiently.
  • How much control you need over the algorithm (full control server-side; possibly limited on a third-party gateway).
  • Whether you already run a gateway for auth/whitelisting — bolt it on there.
  • Engineering time available — a commercial gateway is faster to adopt than building your own.

Example: API allows 2 req/sec; a client sends 3 within a second — the first two pass, the third gets HTTP 429.

04 Algorithms

Counters live in an in-memory cache (Redis is standard) using INCR to bump the count and EXPIRE to auto-clear it — a database would be too slow for this on every request.

Token bucket

Bucket holds up to N tokens, refilled at a fixed rate. Each request spends 1 token; empty bucket → dropped.

params: bucket size · refill rate
  • Simple, memory-efficient
  • Allows short bursts
  • Two params can be fiddly to tune
Leaking bucket

FIFO queue; requests join if there's room, else dropped. Pulled and processed at a fixed outflow rate.

params: queue size · outflow rate
  • Memory-efficient
  • Stable, fixed outflow rate
  • A burst fills the queue with old requests, starving recent ones
Fixed window counter

Timeline split into fixed windows, each with its own counter that resets on a new window.

params: window size · threshold
  • Memory-efficient, easy to understand
  • Edge-of-window bursts can let through ~2× quota
Sliding window log

Keeps every request timestamp (e.g. Redis sorted set); drops stale ones, checks log size against the limit.

params: window size · limit
  • Very accurate — never exceeds the limit
  • Memory-heavy — even rejected timestamps may linger
Sliding window counter

Hybrid: weights the previous window's count by its overlap % with the current rolling window.

params: window size · limit
  • Smooths spikes, memory-efficient
  • Approximation — assumes even distribution in the prior window

Token bucket is the most widely used (Amazon, Stripe). Leaking bucket is used by Shopify.

Sliding window counter — worked example

7 req/min allowed. Previous minute had 5 requests, current minute has 3 so far. A new request lands at the 30% mark of the current minute:

requests in window = current_count + previous_count × overlap%
                   = 3 + 5 × 0.7
                   = 6.5  →  rounded down to 6

6 < 7, so this request is allowed — but the limit hits on the very next one.

05 The fixed-window edge problem

Limit: 5 requests/minute. 5 land in [2:00:00, 2:01:00), 5 more in [2:01:00, 2:02:00) — each window is individually compliant. But the rolling minute [2:00:30, 2:01:30) contains all 10 of them: double the allowed quota.

rolling 1-min window: 10 requests
2:00:00 2:01:00 2:02:00
window 1: 5 requests window 2: 5 requests rolling window (the bug) request

This is exactly the failure mode sliding window log and sliding window counter exist to fix.

06 Deep dive: rules, headers, detailed design

Rate limiting rules

Often config files on disk (Lyft open-sourced their rate-limiting component as a reference example):

domain: messaging
descriptors:
  - key: message_type
    Value: marketing
    rate_limit:
      unit: day
      requests_per_unit: 5

→ max 5 marketing messages/day.

Response headers

HeaderMeaning
X-Ratelimit-RemainingRemaining allowed requests in the current window
X-Ratelimit-LimitMax calls allowed per window
X-Ratelimit-Retry-AfterSeconds to wait before retrying without being throttled

Exceeding the limit returns HTTP 429. Depending on the use case, throttled requests can be queued for later instead of dropped (e.g. orders during system overload).

Detailed design

07 Rate limiter in a distributed environment

Single-server rate limiting is easy. Multiple servers introduce two new problems.

Race condition

Naive flow: read counter → check if counter + 1 exceeds the threshold → write it back.

Locks fix it but slow the system down noticeably. Common alternatives: atomic Lua scripts, or Redis sorted sets.

Understanding the fixes — the book only names these

Every fix below relies on the same trick: don't prevent concurrency, eliminate the gap where it matters — turn the check-and-update into a single indivisible operation on Redis's side. This works because Redis executes commands single-threaded: whatever atomic unit you send it runs to completion before Redis looks at any other client's request.

Fix 0 — just use INCR, not GET+SET

For the plain fixed-window counter, INCR is itself atomic — it increments and returns the new value in one indivisible step. No separate GET, so nothing for a second thread to race against:

newVal = INCR(counter_key)
if newVal == 1: EXPIRE(counter_key, window_size)
if newVal > limit: reject else: allow

This is why Chapter 4's "where to store counters" section named exactly INCR and EXPIRE — INCR already solves the race for the simplest algorithm. The book's race-condition example describes someone reinventing INCR badly with a manual GET → compute → SET.

Fix 1 — Lua scripting, for when one command isn't enough

Token bucket and sliding window counter need to read and write several related pieces of state together — no single Redis command covers that. Ship the whole check-and-update as one Lua script via EVAL. Redis runs the script to completion as one atomic unit, so two concurrent requests against the same key can never both see "tokens > 0" for the last remaining token.

-- token bucket check, runs atomically inside Redis
local tokens = tonumber(redis.call('GET', KEYS[1]) or ARGV[1])
if tokens > 0 then
  redis.call('DECR', KEYS[1])
  return 1   -- allowed
else
  return 0   -- rate limited
end
Fix 2 — sorted sets: the data structure, not the fix by itself

A sorted set (ZSET) is the right shape for sliding-window-log: ZADD to record a timestamp, ZREMRANGEBYSCORE to drop stale ones, ZCARD to count survivors. Each command is atomic alone, but three separate round-trips reopen the same race — another client's ZADD can land between your ZREMRANGEBYSCORE and ZCARD. Sorted sets are always paired with a Lua script or a MULTI/EXEC transaction that bundles all three into one atomic unit. The set gives you the data shape; Lua/transactions give you the atomicity.

Why not just a lock? It works, but rate-limit checks run on every API request — the hottest possible path. Every check now pays for a lock round-trip, and a crash while holding the lock blocks every subsequent request until timeout — a rate limiter bug becomes a full outage. Atomic server-side operations avoid this: there's no lock to acquire or fail to release.

Synchronization issue

The web tier is stateless, so the same client's requests can land on different rate limiter instances — without shared state, each instance's local counter is blind to the others.

Not the fix

Sticky sessions (always route a client to the same instance) work around this, but aren't scalable or flexible.

08 Performance & monitoring

  • Multi-data-center setup — latency is high for users far from the data center; route to the nearest edge server (Cloudflare ran 194 edge locations as of May 2020).
  • Eventual consistency for data sync between rate limiter nodes (see Chapter 6's "Consistency" section).

After launch, monitor whether the algorithm and the rules are actually effective. Rules too strict → valid requests get dropped, relax them. Algorithm falls over during traffic spikes (flash sales) → consider one that tolerates bursts better, like token bucket.

09 Wrap-up talking points

  • Hard vs. soft rate limiting — hard: never exceed the threshold; soft: brief overshoot tolerated.
  • Rate limiting at different OSI layers — this chapter is layer 7 (application/HTTP). Layer 3 (network) rate limiting by IP is also possible, e.g. via Iptables.
  • Client-side best practices to avoid being rate limited:
    • Cache client-side to skip unnecessary repeat calls.
    • Understand the limit; don't burst requests in a short window.
    • Catch exceptions/errors so the client recovers gracefully.
    • Add sufficient backoff time to retry logic.
