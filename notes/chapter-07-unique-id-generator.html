Chapter 7 — Design a Unique ID Generator

auto_increment only works on one database. Across many machines, generating IDs that are unique, numeric, 64-bit, and time-ordered — without constant coordination — takes real design.

01 Why auto_increment doesn't work here

A single database's auto_increment is trivial — one server, one counter. It breaks the moment there are multiple database servers (forced by Chapter 1's sharding or Chapter 6's partitioning): two independent servers each counting 1,2,3... locally will collide the instant their output merges. The real problem: generate IDs unique across machines, without those machines coordinating on every single ID.

02 Requirements

  • IDs must be unique.
  • IDs are numeric only.
  • IDs fit in 64 bits.
  • IDs are ordered by time — not necessarily +1, just: later always means numerically larger.
  • Support 10,000+ IDs/second.

03 Four candidate approaches

Multi-master replication

Native auto_increment, but step by k (number of DB servers) instead of 1, so servers interleave without colliding.

  • Breaks time-ordering across servers
  • Hard to scale across data centers
  • Adding/removing a server reshuffles the whole scheme
UUID

128-bit ID, generated independently per machine, zero coordination. Collision odds are negligible.

  • Trivially simple, scales effortlessly
  • 128 bits (need 64)
  • Not time-ordered
  • Can be non-numeric
Ticket server

Centralize auto_increment on one dedicated DB; everyone else asks it for the next ID (Flickr's approach).

  • Numeric, simple, fine at small/medium scale
  • Single point of failure
  • More ticket servers = right back to multi-master's coordination problem
Twitter Snowflake chosen

Divide the 64-bit ID into sections — timestamp, datacenter ID, machine ID, sequence — each solving one piece of uniqueness/ordering independently.

  • Numeric, 64-bit, time-ordered
  • No SPOF, no cross-machine coordination needed

04 Twitter Snowflake — deep dive

Divide and conquer: split the ID into sections, each independently responsible for one piece of the puzzle.

41-bit timestamp
12-bit sequence
Sign — 1 bit, always 0 Timestamp — 41 bits, ms since custom epoch Datacenter ID — 5 bits (32 DCs) Machine ID — 5 bits (32 machines/DC) Sequence — 12 bits (4096/ms/machine)

Because timestamp sits in the highest-order bits after the sign bit, a later timestamp always produces a numerically larger ID — time-ordering, for free.

Uniqueness without coordination

Every machine has a fixed, unique (datacenter_id, machine_id) pair assigned at startup. Two machines can never collide — even generating in the same millisecond — because that pair differs. Within one machine, the sequence number disambiguates same-millisecond IDs. Datacenter/machine ID are fixed config; only timestamp and sequence are generated live.

05 The math

Timestamp lifespan (41 bits)

  1. Max value = 2⁴¹ − 1= 2,199,023,255,551 ms
  2. ÷ 1000 (ms → s)≈ 2.199 billion seconds
  3. ÷ 3600 ÷ 24 ÷ 365 (s → years)≈ 69.7 years

This is why Snowflake uses a custom epoch (Nov 2010) instead of the standard Unix epoch (1970) — every year already elapsed before your chosen epoch is runway thrown away. An epoch near actual launch buys the full ~69 years.

Throughput per machine (12-bit sequence)

  1. 4,096 IDs/ms × 1,000 ms/s= 4,096,000 IDs/sec per machine
  2. vs. system requirement of 10,000 IDs/sec≈ 400× headroom

Machines can be added freely with zero request-time coordination — uniqueness is structural (datacenter/machine ID), unlike Ticket Server or Multi-master Replication.

07 Wrap-up talking points

  • Clock synchronization — the whole scheme assumes each machine's clock always moves forward. A backward jump (NTP correction, VM drift) could break ordering or risk a collision. NTP is the standard real-world fix.
  • Section length tuning — 41/5/5/12 isn't fixed law. Low-concurrency, long-lived applications might shrink sequence bits and grow timestamp bits for longer runway before overflow.
  • High availability — every write needs an ID, making this mission-critical. Snowflake's payoff: no machine coordinates with any other at request time, so one machine's generator failing never takes any other's offline — the property Ticket Server's SPOF couldn't offer.
